## 1. Test Strategy

The IAAS testing strategy follows a risk-based approach aligned with the testing pyramid, emphasising fast, reliable automated tests at the base while reserving expensive, slower tests for the upper layers where they provide unique value.

### Testing Pyramid

```
         /‾‾‾‾‾‾‾‾‾‾‾\
        /   E2E Tests   \        ← 5% — Critical user journeys
       /   (Playwright)   \
      /‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\
     / Integration Tests      \   ← 25% — API contracts, service interactions
    /   (Vitest + Supertest)   \
   /‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\
  /      Unit Tests              \  ← 70% — Business logic, utilities, components
 /        (Vitest)                \
/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\
```

### Risk-Based Prioritisation

Test effort is allocated proportional to business risk:

| Risk Area | Priority | Test Depth |
|-----------|----------|------------|
| Recommendation accuracy | Critical | Exhaustive — all boundary conditions |
| Authentication/authorisation | Critical | Full coverage — every role × resource combination |
| Financial calculations | High | All rounding scenarios, edge cases, overflow |
| Data validation | High | Malformed input, injection attempts, boundary values |
| Document handling | Medium | Upload/download, virus scanning, size limits |
| UI rendering | Medium | Component snapshots, responsive breakpoints |
| Audit logging | Medium | Event completeness, schema compliance |
| Admin functions | Lower | Happy path + key error scenarios |

## 2. Test Environment

### Local Development

Developers run the full test suite locally using:
- **Vitest** as the test runner (fast, TypeScript-native, watch mode)
- **SQLite** in-memory databases for service tests (zero configuration)
- **Synthetic test data generators** from the `packages/test-data` workspace package
- **Docker Compose** for integration tests requiring full service mesh

### Continuous Integration (GitHub Actions)

The CI pipeline executes on every push and pull request:

```yaml
Pipeline stages:
  1. Lint (ESLint + Prettier check)
  2. Type Check (tsc --noEmit across all workspaces)
  3. Unit Tests (vitest run --coverage) — 659 tests across 39 files
  4. Integration Tests (docker-compose up → test → down)
  5. Security Scan (npm audit + Snyk)
  6. Build Verification (next build for apps)
  7. Deploy to GitHub Pages (static export)
```

**CI Database Configuration:** Tests use `DATABASE_PATH=:memory:` for ephemeral in-memory SQLite databases, ensuring fast execution and complete isolation between test runs. No database server required in CI.

### Test Data

All test data is synthetic, generated by the `packages/test-data` package. No real personal information is used in any test environment. Synthetic data generators produce:
- Realistic but fictional citizen profiles
- Financial scenarios covering all recommendation paths
- Document fixtures (PDF, JPEG) for upload testing
- Edge case data (boundary values, unicode, maximum lengths)

#### Frontend Test Environment (jsdom)

Frontend and backend tests run from a single root `vitest.config.ts` under two different environments. Vitest 1.6 predates `test.projects` (added in v3), so `environmentMatchGlobs` is the supported mechanism at this version — and keeping one config avoids a second runner and a second CI step.

| Setting | Value | Reason |
|---------|-------|--------|
| `test.environment` | `node` | Default, so all 35 backend files are unaffected |
| `test.environmentMatchGlobs` | `[['apps/**', 'jsdom']]` | Opt-in allowlist. A new backend test cannot silently acquire a DOM, which would mask a genuine "this code assumed a browser" bug |
| `test.include` (frontend) | `apps/*/src/**/__tests__/**/*.test.{ts,tsx}` | `__tests__` folders are colocated next to the component under test, at any depth — the convention Next.js app-router nesting pushes towards |
| `test.setupFiles` | `apps/web/src/test/setup.ts` | Vitest applies setup files to *every* test file, so the file guards on `typeof document !== 'undefined'` and no-ops under node, keeping `@testing-library` out of backend runs entirely |
| `esbuild.jsx` | `automatic` | `apps/web` sets `jsx: "preserve"` for Next, leaving esbuild on the classic runtime, which fails with "React is not defined" in files that do not import React |

Libraries (root devDependencies): `jsdom`, `@testing-library/react`, `@testing-library/dom`, `@testing-library/user-event`.

The setup file resolves `@testing-library/react`'s `cleanup` at setup time rather than awaiting the import inside `afterEach` — under fake timers the microtask never flushes, cleanup silently never runs, and components leak into the next test as duplicate event listeners. `cleanup()` in `afterEach` unmounts anything a test rendered; without it, RTL appends each render to the same `document.body` and queries start matching leftovers from previous tests.

**Coverage scope:** thresholds (statements 50 / branches 45 / functions 45 / lines 50) apply to `packages/*` and `services/*` only. `apps/**` is not instrumented, and `services/consolidated-api/**` is excluded as deployment wiring rather than business logic.

**Windows note:** a run may fail with `EBUSY: resource busy or locked` in the temp SSR cache. This is transient file-lock contention from parallel workers, not a test failure — rerun with `--no-file-parallelism`.

### 3.2 Integration Testing

Integration tests verify service-to-service communication and API contracts:

- **API Endpoint Tests** — Every REST endpoint tested with valid requests, invalid requests, and authentication/authorisation scenarios
- **Service-to-Service** — API Gateway correctly routes to downstream services; error propagation; timeout handling
- **Database Integration** — Repository patterns correctly persist and retrieve data; migration scripts apply cleanly
- **External Integration Stubs** — Mock integrations (BASYS, eDEN, DAS, CFT) respond correctly to orchestrator requests

### 3.3 Security Testing

- **OWASP ZAP** — Automated DAST scanning against running services in CI
- **Penetration Testing Approach** — Quarterly manual penetration tests by certified testers (CREST/CHECK)
- **Authentication Tests** — Token validation, expiry handling, session fixation, CSRF protection
- **Authorisation Tests** — Every role tested against every endpoint; privilege escalation attempts
- **Input Fuzzing** — Automated fuzz testing of validation schemas with malformed data

### 3.4 Accessibility Testing

- **WCAG 2.1 AA Compliance** — All public-facing pages must meet Level AA
- **Automated (axe-core)** — Integrated into component tests and CI pipeline; zero violations policy
- **Manual** — Keyboard navigation, screen reader testing (NVDA, VoiceOver), zoom to 400%
- **Colour Contrast** — Verified against GOV.UK Design System contrast requirements
- **Focus Management** — Tab order, focus trapping in modals, skip links

### 3.5 Performance Testing

- **Lighthouse** — Automated Lighthouse CI checks; minimum scores enforced (Performance: 90, Accessibility: 100, Best Practices: 95)
- **PageSpeed Insights** — Core Web Vitals monitoring (LCP < 2.5s, FID < 100ms, CLS < 0.1)
- **Load Testing** — k6 scripts simulating concurrent user loads against API Gateway
- **Response Time Targets** — API responses < 200ms (p95), page loads < 3s on 3G

### 3.6 User Acceptance Testing (UAT)

UAT is conducted with representative users from each role:
- **Citizen journey** — End-to-end application with real device testing
- **Money adviser workflow** — Client management, recommendation review
- **Case officer processing** — Application review, approval, assignment
- **Senior officer oversight** — Reporting, rule management, governance
- **Accessibility UAT** — Testing with users who rely on assistive technologies

## 7. Defect Management

### Classification

| Severity | Definition | Response SLA | Fix SLA |
|----------|-----------|--------------|---------|
| Critical | Security breach, data loss, complete service failure | 1 hour | 4 hours |
| High | Feature broken, incorrect recommendation, auth bypass | 4 hours | 24 hours |
| Medium | Feature degraded, UI issue affecting usability | 1 working day | 5 working days |
| Low | Cosmetic, minor UX improvement, documentation | 5 working days | Next sprint |

### Triage Process

1. Defect raised with reproduction steps and severity assessment
2. Triage within SLA by designated triage lead
3. Assignment to appropriate developer with context
4. Fix development with regression test
5. Verification in test environment
6. Release to production via standard pipeline

### Coverage Gates

- **Minimum coverage:** 85% overall, 90% for recommendation engine
- **Coverage direction:** Must not decrease on any PR (ratchet)
- **New code coverage:** 95% minimum for new files
- **Untested code review:** Any decrease requires explicit justification in PR description

Husky-managed git hooks execute before every commit:
- ESLint (auto-fixable issues corrected, others block)
- Prettier formatting check
- TypeScript type checking (affected files only)
- Fast unit test subset (tests related to changed files)

### Load Testing Approach

Load tests simulate realistic usage patterns:
- **Ramp-up** — Gradual increase from 0 to target users over 5 minutes
- **Sustained load** — Target concurrency maintained for 10 minutes
- **Spike test** — Sudden 3x load increase, measure recovery
- **Soak test** — Moderate load for 2 hours, watch for memory leaks

### Resilience Testing

- **Service failure** — Individual service shutdown; verify graceful degradation
- **Network partition** — Simulated network issues between services
- **Database saturation** — Connection pool exhaustion scenarios
- **Disk space** — Document storage approaching capacity

## 10. Future Testing Enhancements

### Contract Testing (Pact)

Consumer-driven contract tests to ensure service interfaces remain compatible as services evolve independently. Each consuming service defines its expectations, and provider services verify they meet all consumer contracts.

### Chaos Engineering

Controlled fault injection in staging environments to verify system resilience:
- Random service termination
- Network latency injection
- Clock skew simulation
- Resource exhaustion (CPU, memory, disk)

### Mutation Testing (Stryker)

Mutation testing to assess test suite quality by introducing small code changes (mutations) and verifying that tests detect them. Target: 80% mutation kill rate for critical business logic.

### Visual Regression Testing

Automated screenshot comparison for UI components to detect unintended visual changes:
- Component-level snapshots via Storybook + Chromatic
- Full-page screenshots at key breakpoints
- Dark mode / high contrast mode variations

### Property-Based Testing

For the recommendation engine, property-based testing (fast-check) to verify invariants:
- "Every valid input produces exactly one primary recommendation"
- "Confidence score is always between 0.0 and 1.0"
- "Primary recommendation confidence is always >= highest alternative confidence"
- "Output always includes the regulatory disclaimer"
